# ADR-001: Provider-Neutral Session Channels

**Status:** Proposed  
**Date:** 2026-09-15  
**Amendments:** A1-A3, see docs/planning/ADR-001-AMENDMENTS.md (Stage 0, task B3).

## Context
We need secure, active, full-duplex communication between sessions of existing AI harnesses (Claude Code, Codex, Cursor, etc.) without creating another agent harness or model router. Each provider remains responsible for inference, authentication, context, tools, and policy enforcement.

Requirements: push rather than application polling; two-way messaging; authenticated/authorized session identities; simple CLI/home deployment; provider and transport independence; supported provider integration surfaces; commercially usable OSS dependencies where practical.

Claude Code Channels demonstrates the key semantic primitive: an external event can become model-visible input to a live harness session and wake it. Other harnesses expose different surfaces, e.g. Codex App Server and Cursor ACP.

## Decision
Create a provider-neutral **MCP Session Channels extension** with three replaceable layers:

1. **Provider adapters** — translate native harness interfaces to/from Session Channels.
2. **MCP Session Channels** — define identity, addressing, capabilities, messages, replies/correlation, presence, delivery, and security semantics.
3. **Transport plugins** — distribute messages. **Zenoh** is the first reference transport; NATS, MQTT, etc. can follow.

The reference implementation is a CLI and must not require Docker, Kubernetes, a cloud account, or a separately administered server for normal local use.

## Boundary
The project MUST NOT call provider model APIs as a substitute for native harnesses; implement inference/model routing/context management; steal or reuse another harness's provider credentials; depend on UI/terminal scraping or undocumented private RPCs for supported integrations; or leak Zenoh-specific concepts into the neutral protocol.

It MAY use documented MCP extensions, app-server protocols, ACP, hooks, extensions, or other supported IPC, and translate neutral messages into provider-native live-session input operations.

## Architecture
```text
Claude Code       Codex          Cursor          ...
    |               |              |
claude/channel   App Server       ACP
    |               |              |
    +-------- Provider adapters ----+
                    |
            MCP Session Channels
                    |
             Transport API
                    |
          Zenoh | NATS | MQTT | ...
```

## Initial mappings
- **Claude Code:** neutral inbound message -> Claude Channel event; outbound send/reply -> neutral Session Channels operation.
- **Codex:** neutral inbound message -> supported App Server thread/turn input; output/events -> neutral reply/message.
- **Cursor:** expected ACP mapping; deferred unless needed for v0.1 validation.

## Why Zenoh first
Zenoh supports lightweight peer-to-peer pub/sub, discovery/liveliness, secure transports, and optional routing. Local use can avoid a separate broker process. Zenoh remains an implementation detail beneath a neutral transport API.

## Security model
Identity hierarchy:
```text
Security principal -> Device -> Harness -> Session
```
Security layers: authenticated/encrypted transport; default-deny ACL/policy; cryptographic message authenticity; replay protection; optional later E2E encryption. Model-generated text claiming an identity never establishes identity.

Authenticated peer messages remain untrusted instructions and may contain prompt injection. Provenance must remain machine-enforced and distinct from message content.

## v0.1 scope
Include text messages, session identity/addressing, direct messaging, replies/correlation, active push, presence/discovery, authenticated sender identity, authorization hooks, delivery status, Claude adapter, Codex adapter, Zenoh transport, and CLI local deployment.

Defer group rooms/broadcast, attachments, durable offline mailboxes, federation, full E2E encryption, GUI, production Gemini/ChatGPT/Cursor adapters, and alternative transports.

## Alternatives
- **LangGraph/CrewAI/AG2:** rejected; they own model orchestration.
- **A2A:** useful but heavier and not centered on live harness-session wake/injection.
- **Plain MCP tools:** insufficient to define unsolicited live-session input semantics.
- **One hard-coded broker:** rejected; transport independence is required.
- **NATS:** strong second transport candidate; Zenoh wins first prototype because P2P can eliminate a separate broker.
- **RabbitMQ/Redis:** unnecessary deployment burden for the home/CLI target.

## Validation criterion
Architecture is proven when an existing Claude Code session sends through Session Channels/Zenoh to an existing Codex harness session without receiver polling; Codex responds and Claude receives the response actively; neither side invokes or holds credentials for the other's model API; and sender identity/authorization are enforceable rather than inferred from content.
