## 1. Choice

OAC's session identity is a **four-layer model**, and only the first two layers carry
authority:

1. **Device key** — the cryptographic root. A per-device signing key held in the OS
   credential store (§10) or, on the fallback path, an encrypted file (§11). Everything
   else in this hierarchy is anchored to it, per `ADR-001.md`'s identity hierarchy
   `Security principal -> Device -> Harness -> Session` (§12).
2. **Opaque stable OAC session id** — a random, non-derivable identifier bound to the
   device key by a signed registration record (§2, §5). This is the address OAC's own
   protocol carries on the wire.
3. **Display URI** — `session://<device>/<harness>/<id>` (§8), for humans reading logs
   or a CLI listing. Never parsed for authorization, never a wire field.
4. **Human alias** — a local, mutable, per-device label a person assigns (§9). Never an
   identity claim, never transmitted as one.

**Only (a) the device key and (b) the opaque session id carry authority.** (c) the
display URI and (d) the human alias carry none — stated plainly, not left to be inferred
from where they appear in the protocol. A message's routing, authorization, and
provenance decisions are made from (a) and (b) alone; (c) is a rendering convenience and
(d) is local UI sugar. This is the choice, not offered as one option among several.

## 2. Opaque session id construction

**Form.** 128 bits (16 bytes) from the OS CSPRNG, encoded as 26 lowercase Crockford
Base32 characters (alphabet excludes `I`, `L`, `O`, `U` to avoid visual ambiguity — the
same rationale ULID and similar identifier schemes use this alphabet for). No structure
is encoded into the id itself: not a timestamp, not a device fragment, not a harness
tag. This is OAC's own identifier-format decision, not a claim about an external
system, so it carries no first-party citation — it is recorded here as a decision the
way C2 §4 records IPC path forms.

**Generation: random, not derived.** The id is generated by a CSPRNG at registration
time (§5), never computed as a function of the device key, the harness-native id, or
any other input. A derivable-from-device-key scheme is explicitly rejected (§14) because
it would let anyone who observes two session ids from the same device correlate them
back to that device's key material — the opposite of what an opaque id is for.

**Binding to the device key.** "Bound" means the device key has signed a registration
record naming this id (§5) — a cryptographic attestation, not a derivation. Verifying
the binding means checking the signature against the device's known public key, not
recomputing the id from the key. This is the same distinction §14 draws against the
rejected deterministic-derivation alternative.

**Stability.** The id is stable for the life of the OAC session it names — from
registration (§5) until the registering harness-native session ends or, on Claude, a
resume event that is not observed as a re-registration (§6). It never changes value
while that OAC session is live.

**Acceptance box 1, proven here.** "Session ids are opaque and stable; broker-native
addresses are never exposed publicly":

- **Opaque:** the id carries no structure (above) — nothing about it reveals the device,
  the harness, or anything else without consulting the registration record (§5), which
  is daemon-held, not published.
- **Stable:** for the session's life, per the paragraph above.
- **No broker-native address.** The id is Crockford Base32 over random bytes — it
  contains no Zenoh key expression, no Zenoh `zid`, and no other transport-layer
  address form. Per `[ADR-001 Boundary]` "MUST NOT leak Zenoh-specific concepts into
  the neutral protocol," the wire-level session id and Zenoh's own peer/resource
  addressing are two separate namespaces; the transport module maps between them
  internally (`oac-zenoh`), and that mapping never runs in reverse on the wire.
- **No harness-native id.** Claude's `session_id` (§3) and Codex's `thread.id` (§4) are
  captured into the registration record (§5) but are never themselves the OAC session
  id and never appear on the wire in place of it.
- **No working-directory path.** The working directory scopes discoverability (§5) but
  is not encoded into the id string itself.

## 5. The registration record

**What binds native id to OAC id.** A registration record, held by the daemon (per C2 —
the daemon is the single process holding device identity, key material, and session
bookkeeping; `docs/planning/decisions/C2-process-model.md` §1, §5), contains at minimum:

| Field | Content |
|---|---|
| `oac_session_id` | the opaque id (§2) |
| `harness` | which harness registered it (`claude` \| `codex`) |
| `harness_native_id` | `session_id` (Claude, §3) or `thread.id` (Codex, §4) |
| `device_id` | the device this record is bound to |
| `working_directory` | the harness process's working directory at registration |
| `registered_at` | timestamp |
| `signature` | the device key's signature over the record (below) |

**Who signs it.** The device key (§1a) signs the record. This is the proof of binding
§2 names — verification means checking this signature against the device's known public
key, not recomputing the id.

**Where it lives.** Daemon-held, per C2. No client, shim, or harness process holds the
registration record; the daemon is the only writer and the only party that answers
"is this OAC session id valid, and for which harness/device/directory."

**Lifetime.** From registration (§3/§4's capture event) until the daemon deregisters the
underlying session — the same session-lifetime boundary `docs/planning/decisions/
C2-process-model.md` §5 already defines (EOF on the IPC connection ends the session;
daemon exit ends every session under it). The registration record does not outlive the
session it names — durable, cross-restart persistence of registration records is not
built (per `oac-boundaries` 11, durable offline mailboxes are explicitly deferred, and a
persisted registration record that survives daemon restart would be the same kind of
durable store).

**Default-deny rule.** A native id alone never authorizes anything. Presenting a valid
`session_id` or `thread.id` proves nothing about sender authorization by itself — per
`oac-security-work` §4, "Default-deny is the standing posture," and §3's "authenticated
but untrusted" doctrine applies one level down here too: a *registered* session (native
id captured, record signed) is not yet an *authorized* one. Authorization (allowlists,
pairing) is a separate decision, owned by the C5/C6 pairing-and-authorization work
(PLANNING-PROMPT.md §5 decisions 6 and 8), not by registration. Registration answers
"which OAC session id does this native id correspond to"; it never answers "should a
message be delivered to it" or "should this sender's instruction be obeyed."

**Cross-project scoping.** `working_directory` (table above) scopes discoverability: a
session registered from one working directory must not be discoverable by a peer not
authorized for that directory. This is `oac-security-work` §2's checked item verbatim:
"Cross-project leakage: a session in one working directory must not be discoverable by
a peer that is not authorized for it," and matches task H2's fourth acceptance item.
The registration record's `working_directory` field is what the discovery/presence
query (owned by C6/F6, `docs/planning/decisions/C2-process-model.md` §5's presence
model) filters on before a session appears in any peer's discovery result — a session in
`/repo-a` is invisible to a query scoped to `/repo-b` unless a separate authorization
grant says otherwise. This document fixes the field that carries the scope; the query
and grant logic themselves are C6/F6's job, not re-derived here.

## 6. Resume behaviour, Claude

**Tied to the B2 finding, not assumed.** Behaviour across `--resume`/`--continue` is
**UNVERIFIED, docs silent at `v2.1.274`**: "Claude channel behaviour across
`--resume`/`--continue` (issue #12 box 1) — UNVERIFIED, docs silent at `v2.1.274`.
Consequence: OAC's session-identity model may need to re-launch rather than re-attach a
Claude session to guarantee channel delivery. Owner: C-series decision + D1." Source:
`docs/planning/REVERIFICATION-B2.md` "Carried to 11-risks.md" item 1, restated verbatim
from `docs/planning/STATUS.md`'s "Open UNVERIFIED items" list.

**The conservative rule, decided now.** A resumed Claude session is treated as a **new**
OAC session id unless a channel registration is observed for it. Never assume
re-attachment. Concretely: `--resume`/`--continue` produces, from OAC's point of view, a
harness process for which OAC has not yet observed a `SessionStart` hook firing with a
`session_id` it recognizes as continuing a prior registration — until such a hook fires
and the daemon captures a fresh (or matching) `session_id` per §3, OAC has no session to
register at all, resumed or otherwise. If a `SessionStart` hook does fire on resume and
delivers a `session_id`, whatever value it carries is captured and registered as
**a new registration record** (§5) under a **new** opaque OAC session id (§2) — OAC does
not attempt to recognize a resumed Claude `session_id` as "the same" prior OAC session
and does not carry a prior registration's authorization state forward onto it.

**Why this is the correct default, not a guess.** Per `[ADR-001-A2 Amendment]`
(`docs/planning/ADR-001-AMENDMENTS.md` "ADR-001-A2"), the Validation criterion's
"existing session" was redefined as a session **launched OAC-enabled**, not an arbitrary
already-running or reattached one: "a live interactive session, launched OAC-enabled,
whose owner is a human at a terminal, into which OAC injects without owning the
harness's model loop." A resumed session that OAC never observes a fresh registration
event for is not, in OAC's own model, distinguishable from a session that was never
launched OAC-enabled at all — treating it as new, pending observed evidence otherwise,
is the direct application of A2's redefinition to this specific harness behaviour, and
avoids exactly the reach-into-an-arbitrary-session drift `oac-boundaries` boundary 7
warns about: "check before assuming a workaround is needed."

**Risk owner.** **D1**, per `docs/planning/REVERIFICATION-B2.md` "Carried to
11-risks.md" item 1 ("Owner: C-series decision + D1") — this document (the C-series
half) fixes the conservative rule; D1 (Epic D, the Claude gate spike) is the owner of
observing real `--resume` behaviour against the pinned build and confirming or
overturning this rule with runtime evidence.

## 7. Resume behaviour, Codex

`thread/resume` keeps the UUIDv7 `thread.id` (§4) — restart-survival is the cited,
carried fact from PLANNING-PROMPT.md §3.2 (§4 above). Because the identifier itself is
stable across resume, the OAC id **MAY** be re-bound to the same thread: a resumed
Codex thread whose `thread.id` matches an existing registration record's
`harness_native_id` (§5) is registered against the **same** OAC session id, updating the
record's `registered_at` rather than minting a new opaque id. This is the opposite
default from Claude (§6) precisely because the underlying evidence differs — Codex's own
protocol states the id survives; Claude's docs are silent, so §6 does not assume
survival and this section does not assume non-survival.

**The cross-process caveat, verbatim.** Quoted from PLANNING-PROMPT.md §3.2, carried
unchanged per `docs/planning/decisions/C2-process-model.md` §2 leg 4: "Cross-process
resume does not attach. A second app-server process resuming a thread another process
holds loads history from disk and appends silently; the live process is not notified
(open issue #21743)." Re-confirmed still open: `docs/planning/ADR-001-AMENDMENTS.md`
"ADR-001-A2" evidence block — issue #21743 checked directly, `"state": "open"`,
`"closed_at": null`, retrieved 2026-09-16.

**Which process is authoritative for a re-bind, decided.** The OAC daemon's own Codex
app-server client (`docs/planning/decisions/C2-process-model.md` §1, "one client of the
Codex app-server daemon, not one per OAC session") is the only process OAC treats as
authoritative for a `thread.id` re-bind. A `thread/resume` observed by any *other*
app-server process — including a second Codex TUI/Desktop instance resuming the same
thread outside OAC's own client — is not visible to the daemon's client at all (that is
exactly what issue #21743 names: the live process, here the daemon's client, is not
notified). OAC therefore **cannot** re-bind on an out-of-band resume it never observes;
the registration record for that `thread.id` stays as last known to the daemon's own
client until the daemon's client itself either re-observes the thread (its own
`thread/resume`/`thread/started`) or the session is explicitly deregistered.

**On conflict.** If the daemon's own client later observes activity on a `thread.id` for
which a registration record already exists (i.e., the daemon's client itself performs or
observes a `thread/resume`/`thread/started` for an already-registered thread), the
existing registration record is updated in place (same OAC session id, refreshed
`registered_at`) — there is no conflict in this case because the daemon's own client is
definitionally authoritative for what it itself observes. **A true conflict — two
different OAC session ids independently claiming the same `thread.id`** — cannot arise
from this rule, because only the daemon's own client ever writes a registration record
(§5, "daemon-held ... the daemon is the only writer"); it is not a case this decision
needs to arbitrate between two writers, since there is exactly one. What the rule does
**not** solve, and does not claim to: silent history-append by an out-of-band second
app-server process (the #21743 hazard itself) is invisible to OAC entirely — OAC's
registration record reflects only what the daemon's own client has observed, which may
lag behind the thread's true state if another process appended to it unobserved. This
gap is named, not hidden: it is the same gap `docs/planning/decisions/C2-process-model.md`
§2 leg 4 already names as the reason a single daemon-owned client is the chosen
architecture in the first place (one client instead of N, so this exact hazard is faced
once, not N times).

## 8. Display URI form, and C8's resolution

**Form.** `session://<device>/<harness>/<id>` — `<device>` a short device label,
`<harness>` `claude` or `codex`, `<id>` the opaque session id (§2). Example:
`session://laptop-01/claude/01harn7x9k2m4p6q8r0s2t4v6w`.

**Display-only, stated in full.** The display URI is:

- **Never parsed for authorization.** No code path that grants access, checks an
  allowlist, or verifies a signature reads this URI form — those checks operate on the
  registration record (§5) and the opaque id (§2) directly.
- **Never a wire field.** OAC's envelope and protocol messages carry the opaque id
  (§2); the display URI does not appear in any wire-format message this document or
  `docs/planning/DESIGN.md`'s envelope shape defines.
- **Never a routing key.** Delivery is addressed by opaque session id; nothing routes a
  message by parsing `<device>`/`<harness>` out of a URI string.

It exists for humans — CLI listings (`oac sessions`, `docs/planning/decisions/
C2-process-model.md` §6), logs, and debugging output — exactly the use
`docs/planning/DESIGN.md`'s Addressing section names: "a URI such as
`session://device/harness/id` may be useful for display."

**C8, stated explicitly.** Conflict C8 (`docs/planning/ADR-001-AMENDMENTS.md`, C8 row,
conflict-register table): "DESIGN suggests session ids may map to a URI containing
device and harness; ADR requires no leak of transport concepts." The apparent tension:
`docs/planning/DESIGN.md`'s Addressing section suggests a display URI naming device and
harness, while `[ADR-001 Boundary]` forbids leaking Zenoh-specific concepts into the
neutral protocol.

**Resolution.** These are not actually in conflict, once "transport concepts" is read
correctly (as ADR-001's own boundary text reads, and as `docs/planning/DESIGN.md`'s own
elaboration reads: "The specification MUST NOT mention Zenoh keys, MQTT topics, NATS
subjects, or provider-specific method names"). The display URI's `<device>` and
`<harness>` components are **not** Zenoh concepts — they are OAC's own neutral
vocabulary (a device, per the identity hierarchy §1/§12; a harness, the same neutral
term `ADR-001.md`'s Security model itself uses). The boundary is about Zenoh key
expressions, liveliness tokens, and similar transport-native vocabulary leaking into the
spec — not about whether a *display* string may mention which device or harness a
session belongs to, which is exactly the "descriptive metadata" `docs/planning/
DESIGN.md`'s Addressing section itself invites: "Consider opaque stable session IDs with
descriptive metadata." The URI leaks nothing Zenoh-specific (no `zid`, no key
expression, no liveliness term appears in its form above), is non-authoritative (per the
three bullets above), and the wire carries the opaque id only. C8 is **closed as stated,
with no ADR-001 text needing correction.**

**RESOLVED-IN-DECISION, no numbered amendment.** Unlike `ADR-001-A1`/`A2`/`A3`, this
resolution corrects no verbatim text in `ADR-001.md` — nothing in the ADR's Boundary or
Security model sections is wrong or contradicted by this section's conclusion (the same
test C1 §2 applies when it declines an amendment for its own single-binary-packaging
clarification: "not the kind of 'evidence invalidates a settled decision' case
`oac-evidence` §6 amends for"). C8 is marked **`RESOLVED-IN-DECISION`** in the conflict
register, pointing at this section — a new status distinct from `RESOLVED-HERE` (which
names an A-amendment inside `ADR-001-AMENDMENTS.md` itself; C1's and C2's rows use it
because `ADR-001-A1`/`A2` live there) and from C3's own `RESOLVED-BY-DECISION` (which
pairs an A-amendment, `ADR-001-A3`, with a separate decision document for the
identifier). C8 has neither: no A-amendment at all, only this decision document. See
`docs/planning/ADR-001-AMENDMENTS.md`'s conflict-register legend for the exact
definition.

## 9. Human aliases

A human alias is a **separate namespace**, local to a device, mutable at will, and
**never transmitted as an identity claim**. An alias maps, on one device, a
human-chosen label to an opaque session id or a display URI (§8) — e.g. a person types
`work-codex` in their own CLI and OAC resolves it locally to the current session id it
points at. This mapping lives only on the device where it was created; it is never sent
to a peer, never included in an envelope, and never an ACL subject (§14 rejects that
alternative explicitly).

**Model-facing consequence.** Per `oac-security-work` §3 and §5: an alias appearing in
message *content* is content, not provenance. If a message's text says "this is from
`work-codex`," that string is exactly as untrusted as any other model-generated or
user-typed text — the authenticated-but-untrusted doctrine applies without exception:
"An authenticated peer message is still an untrusted instruction ... Authentication
answers 'who sent it.' It never answers 'should this be obeyed.'" Provenance (sender,
device, session — §12's machine-set metadata) is what actually identifies a message's
origin, rendered per `oac-security-work` §5's per-provider rule (Claude `meta`
attributes; Codex's machine-generated header); an alias never substitutes for it and is
never checked as if it did.

**Why `age` over the RustCrypto primitive composition (`chacha20poly1305` `0.11.0` +
`argon2` `0.6.0`, both MIT OR Apache-2.0, repository `RustCrypto/AEADs` and
`RustCrypto/password-hashes` respectively — checked as the rejected alternative, not
picked from memory; crates.io metadata retrieved 2026-09-17).** Composing
`chacha20poly1305` and `argon2` directly would require OAC to design and version its own
file format (salt placement, KDF parameters, AEAD nonce handling, framing) from scratch;
`age`'s `scrypt::Recipient`/`scrypt::Identity` pair already is a complete,
already-specified file format (`age-encryption.org/v1`) with an independent Go reference
implementation to cross-check against, and OAC's own device-key blob is exactly the kind
of small, single-recipient secret this format targets. Choosing the pre-specified format
over inventing OAC's own is the smaller design, matching the same "smallest design that
proves the criterion" preference `docs/planning/decisions/C2-process-model.md` §8 already
applies to the process model.

**When the fallback engages.** Per C1 §8/§9's runtime-dependency note: the Secret
Service backends (`zbus-secret-service-keyring-store` / `dbus-secret-service-keyring-store`)
"require a running D-Bus session bus and a Secret Service provider (e.g. `gnome-keyring`,
`kwallet`) to be present at runtime — a system service dependency ... a real one on
headless/minimal Linux hosts." The encrypted-file fallback engages specifically on
**headless Linux with no Secret Service session bus reachable** — i.e., when neither the
`zbus`/`dbus` Secret Service backend nor `linux-keyutils-keyring-store` (§10's
Secret-Service-free alternative) can be used or is selected for the build, `keyring`
itself returns an error attempting to open the platform store, and OAC falls back to the
`age`-encrypted file instead of failing outright.

**Passphrase/KDF source.** The `age::scrypt` recipient's KDF is `scrypt`, internal to the
`age` crate (per its own dependency graph — `scrypt.workspace = true` in the fetched
`Cargo.toml`, §11 above) — OAC does not implement or select its own KDF. The passphrase
itself is **not** interactively prompted at every daemon start (that would break C2 §7's
"zero-file local default" / "fresh install with no config file works" expectation for
the common OS-keyring path, and would make the headless-fallback path materially harder
to automate than the primary path). Instead: on first fallback-path key creation, OAC
generates a random passphrase itself (CSPRNG, same primitive class as §2's session-id
generation) and stores *that* passphrase — not the device key — as the thing a headless
deployment's own secret-management story (a systemd credential, an environment variable
injected by the host's own secrets manager, or an operator-supplied value) is responsible
for protecting. Which of the concrete delivery mechanisms (systemd credential vs. env
var vs. operator-supplied file) a given headless deployment uses is a Stage 3/6
implementation and packaging detail (`oac-implementation`, `oac-release`), not fixed by
this document.

**Override of the source's own guidance, recorded per `oac-evidence` §6 rather than
silently followed or silently ignored.** `age`'s own documentation, quoted above,
directs a CSPRNG-generated secret to `x25519::Identity`, not `scrypt::Recipient` — this
decision uses `scrypt::Recipient` anyway. This is a deliberate override, not an
oversight, for one reason: switching to `x25519::Identity` does not remove the
underlying problem `scrypt::Recipient` is chosen to help with, it only relocates it.
Either way, OAC ends up with one machine-generated secret (a passphrase, or an
`x25519::Identity`'s private key) that a headless deployment's own secrets
infrastructure must protect — an `x25519::Identity` private key is not self-protecting
either. What `scrypt::Recipient` adds that `x25519::Identity` does not is the KDF's
deliberate work-factor: if the `age`-encrypted file is exfiltrated by itself, without
the passphrase (the file and the secret it depends on are stored separately, by
design — the file on disk, the passphrase in the host's secrets manager), `scrypt`
imposes a real per-guess cost on any offline attack against the exfiltrated file,
exactly as it would for a weak human passphrase. An `x25519::Identity` gives an
attacker who obtains the private key immediate, cost-free decryption with no equivalent
margin. This trades a documented "should only be used with a human ... passphrase"
recommendation for a specific, stated defense-in-depth property this decision's threat
model (§13, "Device-key exfiltration from the fallback file") wants: the file alone
should not be enough. Recorded here as an explicit, evidence-aware deviation, not an
unexamined reuse of the passphrase API's default-shaped use case — if this reasoning is
later found wrong (for example, if the KDF work-factor is shown not to matter against
the real deployment's threat model), reverse to `x25519::Identity` and update this
section rather than silently keeping the reasoning stale.

## 12. Credential boundary self-check

Restating `docs/planning/decisions/C1-language-runtime.md` §8's boundary note in this
document's own terms: **the credential store — OS keyring (§10) or encrypted-file

- **OAC MUST NOT read any Claude Code OAuth token.**

**Boundary 5 check — no Zenoh concepts in the id or URI.** Confirmed by re-reading §2
and §8: the opaque session id is Crockford Base32 over random bytes (§2); the display

`[ADR-001 Boundary]` "MUST NOT leak Zenoh-specific concepts into the neutral protocol."

id (§2) and the device key (§1a, §10, §11) identify an OAC session and an OAC device;

Codex in place of the harness's own authentication. Quoted: `[DESIGN Non-goals]`
"Replacement provider auth" is out of scope, per `oac-boundaries` 10.

## 14. Rejected alternatives

- **Harness-native id used directly as the OAC address.** Rejected: `session_id` and
  `thread.id` are provider-native identifiers OAC does not control the format, stability
  guarantees, or lifecycle of; using either directly as OAC's own wire address would
  make OAC's protocol hostage to a research-preview/experimental surface's own id
  scheme, and would leak the harness-native id onto the wire (§2's "no harness-native
  id" acceptance-box requirement).
- **Id derived deterministically from device key.** Rejected: leaks device identity —
  anyone who observes two ids derived from the same device key could correlate them
  back to that device without ever seeing the key itself, defeating the point of an
  opaque id (§2).
- **URI as the wire address.** Rejected: the display URI (§8) encodes device and
  harness for human readability; using it as a routing key would mean the wire format
  itself carries device/harness metadata on every message, which is more than the
  opaque id needs to expose and moves exactly the kind of descriptive metadata
  `docs/planning/DESIGN.md`'s Addressing section scopes to "display" into the
  authoritative path instead.
- **Alias as an ACL subject.** Rejected: aliases are local, mutable, and never
  transmitted (§9) — an ACL subject must be something the granting party and the daemon
  both stably agree on, which a per-device human label is not.
- **Keys in a plain config file.** Rejected: defeats the entire purpose of §10/§11's OS
  credential store and encrypted-file fallback — a plaintext key file is readable by
  anything with filesystem access, the exact device-key-exfiltration threat §13's fifth
  row exists to mitigate.
- **A custom OS-keystore wrapper instead of `keyring`.** Rejected: `keyring` `4.2.0`
  already provides per-platform backends for every target OAC supports (§10), is
  already pinned and evidenced in `docs/planning/decisions/C1-language-runtime.md` §8,
  and a custom wrapper would duplicate that work while introducing new,
  independently-unverified platform-API code for no offsetting benefit.
