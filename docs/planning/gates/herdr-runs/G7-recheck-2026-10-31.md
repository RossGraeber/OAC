The row 73 states were chosen because the rust-v0.166.0 source reading the scenario header cites
(`codex-rs/app-server/src/request_processors/thread_processor.rs` L4697 to L4748, read 2026-10-31) makes the outcome
depend on subscribers. The override is applied only to a thread that is loaded, idle, has no subscribers and is not
running; otherwise it is ignored with a warning and the thread is rejoined. The `approvalPolicy` member was chosen
because it is the one of the six members that MCPB-CDX-006 names which is harmless and observable.

## What it shows

- **Row 66 (a), both halves, on 0.166.0.** Items queued before a turn was interrupted waited through a 25 s quiet
  window, then ran one per idle, in order, after the next uninterrupted turn. An add to an idle thread whose last
  turn was interrupted waited the same way. This is what the 0.161.0 run recorded (`11-risks.md` row 66).
- **Row 66 (c) and (d).** An add to an unloaded thread waited, and `thread/resume` dispatched it. An extra member in
  `thread/queue/add` was accepted and had no effect: the message ran with the text the client sent.
- **Row 66 (b), now CONFIRMED.** A second daemon client, one that had never started or resumed the thread, listed,
  updated, reordered and deleted queued items with `thread/queue/list`, `thread/queue/update`,
  `thread/queue/reorder` and `thread/queue/delete`. These methods are experimental in the schema (the scenario header
  names how it checked them). Dispatch followed the changes. So an item OAC reports as `handed-to-harness` can be
  altered or dropped by another daemon client while it is held. The run showed this on items held after an interrupted
  turn, the window in which a queued item waits. This is a daemon behaviour, not something OAC's send
  does or can prevent.
- **Row 73, answered on the wire.** A `thread/resume` with `approvalPolicy` `untrusted`, on a thread that is `on-request`,
  is not applied to a loaded idle thread that has subscribers. It is applied and kept for a loaded idle thread that has
  no subscriber, and for a thread that is not loaded. "Kept" means a later resume, while the thread was still loaded,
  reported the new value; persistence across unload or restart was not shown. One run, on Windows. This matches the source reading above. MCPB-CDX-006 (send no
  setting member on a subscribing resume) protects against a real effect, the no-subscriber case.

## What it does not show

- **Row 73 is a wire-level observation.** No turn was started after an override, so what the app-server does with
  the override inside a turn is not observed (the manifest caveat, above). The no-subscriber branch was judged in the
  state before the override's own resume subscribed, which the scenario arranged.
- **Row 66 (b) rests on experimental methods.** The `thread/queue/*` management methods are experimental. They are not
  yet in the `oac-codex-appserver` skill or in the spec's schema tables, and this run does not say how stable they are.
- **One run, n = 1**, against one daemon (0.166.0) on one machine.
- **Windows only.**
- Nothing here changes a gate verdict, a spec normative text or the spec's bindings. `spec/bindings/mcp.md` §8.2.1 is
  for the lead to read against 66(b); it was not edited here.
